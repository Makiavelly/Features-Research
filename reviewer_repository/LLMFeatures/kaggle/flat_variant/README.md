Импортировать **`../llmfe_llama31_hm_flat_kaggle_t4.ipynb`** в отдельный Kaggle Notebook.
Input прежний: **`hm_llmfe_kaggle_fulltrain_v2.zip`**. Включить T4 и Internet, Run All / Save Version.
Все runtime-модули встроены; отдельные .py/репозиторий загружать не нужно.
По умолчанию официальный hf и ревизия `0e9e39f249a16976918f6564b8830bc894c89659`,
как в успешной balance-scale диагностике. Нужен HF_TOKEN с доступом к модели.
MODEL_SOURCE=`unsloth` также сохранён; SHA официальной модели не переносится на другой репозиторий.
NF4/double quant/FP16, temperature0.8, chat template. XGBoost здесь не используется и не устанавливается.

Новый protocol: `hm_llmfe_llama31_8b_lightgbm_flat_fulltrain_v1`.
Старые ноутбуки/результаты не изменяются. Фактический run ID включает хеш модели/пакетов/кода/данных.

## Что получает Llama

Одна готовая числовая таблица X. Строка — кандидатная пара покупатель–товар.
Никаких history, SQL, группировок и соединений в программе Llama.
Функция `modify_features(X)` создаёт преобразования существующих столбцов и возвращает DataFrame.
Как в диагностике, допускается удалять менее полезные столбцы; тогда эффект включает отбор признаков.
Названия новых колонок произвольные строки; нет требования выучить отдельный JSON-язык.
Строки/индекс/схема должны сохраняться; числовой выход1–78 колонок.
Преобразования только по одной строке: отношения/произведения/log/recency/affinity.
Обучение, статистики по текущему батчу, groupby/merge/rolling и внешние данные запрещены.
Preflight сравнивает результат целой выборки и её половинок, отклоняя зависимость от размера батча.

30 базовых колонок:

- 15 исходных customer/article полей `raw_u_*`/`raw_i_*`;
- счётчики прошлых покупок пользователя и товара за7/30/180 дней (6 колонок);
- давность последней покупки пользователя и товара (2);
- средняя прошлая цена пользователя и товара (2);
- покупки пользователем типа кандидатного товара за30/180 дней (2);
- счётчик и давность покупки этой пары user–article (2);
- покупки пользователем цвета кандидатного товара за180 дней (1).

Все15 исторических агрегатов заданы человеком, это **не LLM-признаки**.
Вычисляются один раз для каждого cutoff по прошлым180 дням, только в заданной когорте,
после чего кэшируются в working. Llama получает исключительно30 числовых колонок,
без ID, целей, timestamp, истории и служебных индексов кэша.

## Контроли и честное сравнение

1. `raw15_control`: LightGBM на исходных15 полях.
2. `raw_control` / Prepared30 LightGBM в графиках: исходные поля+15 ручных агрегатов.
3. `seed_control`: **Seeded32**, Prepared30+2 ручных `log1p` преобразования счётчиков.
4. LLM-модель: трансформация той же Prepared30 таблицы; стартовый Seeded32 реально обучен
   и оценён до первой генерации. Его код всегда показан в промпте, не только описание формата.

Главное сравнение вклада Llama — с Prepared30 и Seeded32, а не только с Raw15.
Рост Prepared30 относительно Raw15 относится к ручной подготовке истории.
Победить может любой host-контроль: итог явно отмечает NO LLM features.
Начальные программы/контроли не входят в20 успешных LLM-наборов.
Сохранённые manual126/GNN→LightGBM/ID-GNN оцениваются по тем же пользователям и пулам.
У GNN иной бюджет upstream-обучения, протоколы подбора старых деревьев отличаются.

Прежние803377 train пар/50000 user-times/52 снимка. Исходный Input не меняется.
В кэшированные копии пар добавлены служебные `_flat_row`/`_flat_split`; исходные столбцы,
метки, порядок и число строк проверяются на точное совпадение. Служебные поля Llama не видит.
LightGBM150 rounds/31 leaves, все seeds42, до4 CPU threads.
Search256/confirm512/heldout val1024/test2048 пользователей, те же кандидаты ID-GNN.
Выбор только по search/confirmation, val/test после фиксации программы.

## Бюджет и выходы

Три популяции,3 новых предложения на один prompt, до3 предыдущих измеренных программ.
Цель20 различных успешно оценённых программ, максимум300 обращений, до3 исправлений.
Дедупликация по нормализованному AST, не доказательство математической уникальности формул.
**Пилот:** если после первых6 обращений0 успешно оценённых наборов, остановка с ошибкой и ZIP.
Если успех есть, поиск автоматически продолжается в пределах20/300/3.
Не считать прохождение preflight измерением качества; успех только после полного LightGBM+search MAP.

После завершения ZIP в Output: сравнения, гистограммы AP, парные разницы, learning curves,
search_progress, request/prompt/response/trial/program для каждого обращения, сохранённые деревья,
независимый replay предсказаний, config и flat manifest.
При ошибке подготовки/контролей/загрузки/поиска/финала предусмотрен failure ZIP.
Остановка процесса/отмена Save Version не гарантирует выполнение обработчика ошибок.

Локальные проверки — настоящая подготовка данных и LightGBM с **тестовыми программами**,
а не генерация настоящей Llama. Тестовые метрики не являются итогом нового LLM-эксперимента.
Настоящую Llama/T4 нужно запустить в Kaggle; успешная balance-scale диагностика не гарантирует
валидные/полезные ответы в H&M. Это адаптация идеи, не численное воспроизведение статьи.
