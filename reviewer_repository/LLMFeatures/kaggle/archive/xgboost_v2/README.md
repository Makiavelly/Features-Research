# Kaggle T4: Llama3.1-8B, H&M, одинаковые803377 train пар

Основной файл: [llmfe_llama31_hm_kaggle_t4.ipynb](llmfe_llama31_hm_kaggle_t4.ipynb).
Самодостаточный Jupyter-ноутбук; `.py`-модули автоматически создаются из встроенной ячейки.
Клонирование этого репозитория и загрузка отдельных скриптов не нужны.

## Запуск

1. Выберите источник в конфиге ноутбука: `MODEL_SOURCE = 'unsloth'` (по умолчанию)
   или `MODEL_SOURCE = 'hf'`. Оба репозитория размещены на Hugging Face.
   Для `unsloth` используется публичный `unsloth/Meta-Llama-3.1-8B-Instruct`, без токена.
   Для `hf` получите доступ к [meta-llama/Llama-3.1-8B-Instruct](https://huggingface.co/meta-llama/Llama-3.1-8B-Instruct):
   аккаунт HF, подтверждённая почта, форма/условия на странице модели, одобрение доступа.
   Для ручной проверки гарантированного срока нет.
2. Только для `hf`: создайте HF token с правами Read для того же аккаунта.
3. Создайте Kaggle Dataset из **hm_llmfe_kaggle_fulltrain_v2.zip** и добавьте его в Input ноутбука.
   Можно прикрепить ZIP или автоматически распакованные Kaggle файлы — оба варианта поддержаны.
4. Импортируйте `.ipynb` в Kaggle. Выберите **GPU T4**, включите Internet.
   При T4×2 используется только GPU0; распределение на две карты не требуется.
5. Только для `hf`: Add-ons → Secrets: добавьте `HF_TOKEN`, включите доступ для этого ноутбука.
6. Run All. Скачайте итоговый `hm_llmfe_llama31_8b_fulltrain_v2_<hash>_results.zip` из Output.

Модель скачивается с HF, а не из нашего архива. Загрузка исходных весов требует
примерно16GB диска до квантизации; итоговый GPU footprint выводится в ячейке.
В Kaggle нужны свободные GPU/RAM/диск. Токен в артефакты не записывается.

```python
MODEL_SOURCE = 'unsloth'  # публичная публикация Unsloth, анонимная загрузка
# MODEL_SOURCE = 'hf'    # официальный Meta, одобренный доступ и HF_TOKEN
MODEL_REVISION = ''     # либо конкретный commit SHA выбранного репозитория
```

Вариант Unsloth не требует установки библиотеки Unsloth: обычный Transformers
загружает полноразмерные веса и квантизует их в NF4 так же, как официальный источник.
Здесь не используется отдельный предварительно квантизованный `-bnb-4bit` репозиторий.
Для публичного источника передаётся `token=False`: сохранённый/отклонённый токен
не будет случайно использован. Переключения при ошибке нет. Источник, repo ID и
ревизия записываются в run_config.json/model_runtime.json и меняют хеш run ID.
Побитовое совпадение весов издателей не проверено; лицензия Llama сохраняется.

## Данные и сравнение

- Полные исходные **803377 train пар /50000 user-times /52 временных снимка**.
  `train_pairs.parquet` скопирован побитово из локального кэша, SHA256 совпадает.
  Новые пары и негативы не выбираются.
- Search256 пользователей /6594 пары; confirmation512 /14687.
- Итоговая validation1024 /28040; test2048 /57296.
- Три validation-выборки не пересекаются. Данные test используются после фиксации программы.
- Ровно сохранённые кандидаты ID-GNN seed42, без добавления позитивов из целей.
- История1,688,050 транзакций для выбранной когорты пользователей; каждый вызов программы
  видит только свои прошлые180 дней. Глобальная популярность относится к когорте, не всему H&M.
- Статические категории компактно перекодированы одинаково в X и history;
  соответствия сохраняются в schema.json. ID используются только как ключи.
- Референсы ручного LightGBM и GNN→LightGBM — сохранённые top12 ранее обученных моделей,
  выбранные для тех же строк/кандидатов. Оба дерева использовали те же803377 train пар.
  Native ID-GNN также включён отдельной строкой, с оговоркой о графовом обучении.

Финальная таблица: raw XGBoost, LLM→XGBoost, raw LightGBM, LLM→LightGBM,
ручной LightGBM, GNN→LightGBM, native ID-GNN. Основное сравнение трёх способов —
**LLM→LightGBM /ручной LightGBM /GNN→LightGBM** на одинаковом выбранном test.
Число пар одинаковое, но это ещё не строгий изолированный эффект признаков:
старые деревья подбирали листья15/31 на других10000 val строках и использовали
другие производные seeds. У GNN есть стоимость предварительного обучения.
Новая итоговая validation не участвовала в новом поиске, но может пересекаться
со старым tuning validation референсов. Test остаётся финальной общей оценкой.

Нельзя сравнивать новый MAP по2048 test пользователям с прежним MAP по67144:
используйте пересчитанную таблицу из ноутбука. Текущий локальный H002 не меняется.

## Что сохранено из исследования и что изменено

Используем одну из моделей исследования, Llama-3.1-8B-Instruct, temperature0.8,
3 независимые популяции, до3 программ в prompt,3 сэмпла одного prompt и20 программ
всего. Программы — Python/pandas. Память группируется по MAP; демонстрации выбираются
с помощью Boltzmann sampling. Квантизация NF4 — изменение для размещения на одной T4.
Три сэмпла исполняются последовательно, чтобы не увеличивать VRAM из-за batch3.

XGBoost оценивает программы150 rounds; после поиска top3 проходят отдельную confirmation.
Контроль без новых признаков может победить. После фиксации программы LightGBM150 rounds,
31 лист обучается на тех же признаках; эти результаты не изменяют выбранную программу.
Поиск ориентирован на XGBoost: это не отдельная оптимизация признаков под LightGBM.

Ошибки/дубликаты расходуют общий бюджет20 программ, как в ограниченном поиске статьи,
в отличие от локального H002 с отдельным целевым числом удачных наборов. Автоматических
LLM-исправлений в этом варианте нет. Число фактически оценённых наборов показывается явно.

Лимиты:30с на вызов функции,4GiB адресного пространства evaluator,1800с на полный
этап обучения/оценки. Статья указывает30с/2GB для полной оценки; эти лимиты не удалось
сохранить для803377 пар.4GiB здесь — CPU-память, а не VRAM. Это адаптация H&M ranking,
не воспроизведение опубликованных classification/regression метрик или всех условий статьи.
Настройки, ревизия Llama, квантизация, пакеты, данные и evaluator хешируются в новом run ID.

Источники: [статья](https://arxiv.org/html/2503.14434v3),
[код авторов](https://github.com/nikhilsab/LLMFE),
[модель](https://huggingface.co/meta-llama/Llama-3.1-8B-Instruct),
[NF4/float16](https://huggingface.co/docs/transformers/v4.57.1/quantization/bitsandbytes).

## Локальная проверка

Формат notebook/AST, хеши, одинаковые train пары, непересечение val-подвыборок,
исключение будущих транзакций/меток, ранжирование и MAP проверяются `test_notebook.py`.
Полный raw XGBoost действительно обучен на803377 парах в CPU-проверке.
`check_integration.py` использует явно синтетический генератор и малые данные:
проверяет ошибки, дубликаты, четыре новых дерева, независимый replay, resume и графики.
Его метрики — **smoke, не результат Llama**. Проверки лежат отдельно в
`reports/kaggle_llmfe_validation`. Рабочий GPU-инференс Llama на Kaggle здесь не выполнялся;
его должен запустить пользователь. Пакеты проверок установлены только в `.check-deps`,
текущие ML-окружения не менялись. Скрипты нужны лишь для сопровождения и пересборки.
