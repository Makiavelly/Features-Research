# Контекст для обсуждения улучшений API GPT feature engineering

Я исследую автоматическое построение признаков для рекомендаций H&M. Ниже фактические условия нашего эксперимента. Помоги выбрать следующие эксперименты: отделяй подтверждённые факты от гипотез и не предполагай, что LLM уже доказанно лучше обычного feature engineering.

## Задача и данные

Для каждого пользователя в дату отсечения нужно ранжировать товары, которые он купит в следующие семь дней. Результат — 12 товаров в порядке приоритета. Позиции списка не соответствуют дням недели. Основная метрика — MAP@12.

Используется фиксированная подвыборка H&M: 20 000 пользователей, 10 000 доступных для рекомендации товаров, 260 295 транзакций в подготовленной базе. Пользователи выбраны среди активных за90 дней до29 июня2020; каталог — популярные товары внутри этой когорты за предшествующие180 дней. Состав когорты/каталога фиксируется без будущих целей. Старые5000 пользователей малого пилота исключены. Это ограниченный каталог, а не весь H&M.

История содержит только известные к текущей дате покупки. В признаки не поступают будущие транзакции или целевые покупки. Более поздний фолд может использовать покупки из прошедшей тестовой недели предыдущего фолда как уже известную историю: это намеренная rolling-origin оценка. Статические характеристики взяты из предоставленного снимка H&M; историческую доступность каждого статического поля гарантировать не можем.

Есть три временных фолда. Даты начала outer-test недель:17 августа,31 августа и14 сентября2020. Inner validation — предыдущая неделя. В каждом фолде обучение использует шесть предшествующих недельных срезов; последние обучающие цели заканчиваются к началу inner validation. Поиск программ и диалоги LLM начинаются независимо для каждого фолда. Seed обучения —42.

| Фолд | Обучающие user-times | Обучающие пары пользователь–товар | Search пользователей | Confirmation | Outer-test пользователей |
|---|---:|---:|---:|---:|---:|
|0|10 923|190 260|256|380|1 839|
|1|9 583|166 670|256|420|1 982|
|2|8 548|148 100|256|382|1 698|

User-time — один пользователь в один недельный cutoff; один человек может встречаться в нескольких срезах. Все сравниваемые деревья обучаются на одних сохранённых парах: все обучающие положительные примеры, до8 отрицательных товаров из истории и до8 случайных отрицательных на user-time. Seed генерации отрицательных —2026. Нейросети используют те же обучающие user-times/положительные цели, но их собственные функции потерь и эффективное число примеров отличаются.

## Что делает LLM

LLM пишет полную функцию:

```python
def modify_features(X, history):
    # pandas/NumPy: построение признаков
    return features_dataframe
```

Это генерация кода построения признаков. LLM не обучает деревья, не выдаёт пользователям рекомендации напрямую и не создаёт здесь текстовые embeddings.

`X` — текущие пары-кандидаты: customer_id, article_id и15 статических числовых/закодированных полей. Пользовательские поля: возраст, FN, Active, статус участника клуба, частота новостной рассылки. Товарные: product_code, тип товара, графический рисунок, цветовые категории, department, index_group, section, garment_group.

`history` — таблица прошлых покупок всей фиксированной когорты, доступных на текущий cutoff. Поля: customer_id, article_id, price, sales_channel_id, days_ago, десять категориальных характеристик купленного товара и customer_age. Категории в X и history согласованы по кодировкам. Целей и будущих строк в этих входах нет. Используется вся сохранённая доступная история, а не обязательное окно180 дней; функция сама выбирает окна через days_ago. Цена нормализована; события — покупки, не просмотры.

Разрешены pandas/NumPy, groupby/agg/map/merge, формулы и вспомогательные функции. Другие библиотеки, I/O, сеть, eval/query, случайность и приватные атрибуты запрещены. Эта реализация снижает риск ошибок и нежелательного I/O, но не является полноценной песочницей для враждебного кода.

Выход — DataFrame из1–36 числовых столбцов `f_*` с исходным индексом и порядком X. ID возвращать нельзя. Только эти столбцы поступают в LightGBM:15 исходных полей автоматически НЕ добавляются. Если LLM хочет оставить возраст или категорию, она должна явно вернуть их как собственные `f_*` признаки. Возвращённые f_* сейчас рассматриваются деревом как числовые; категориальные f_* автоматически не объявляются категориальными. Пропуски и бесконечности заменяются на−1.

Каждая программа задаёт полный набор признаков. Отдельные признаки не оцениваются и не накапливаются автоматически в общий пул; сравниваются программы целиком.

## Что модель получает в запросе

Промпт описывает задачу максимизации validation MAP@12, все доступные поля и ограничения. Есть работающий небольшой пример функции, три примера статических обучающих строк без labels, лучшая программа своей популяции и её search MAP. При исправлении добавляются предыдущий полный ответ и диагностика ошибки.

LLM не получает всю таблицу обучения, все строки истории, полную статистику распределений, feature importance или подробный разбор пользователей, на которых модель ошибается. Она предлагает код по схеме/примеру/собственной истории попыток и полученному fitness.

Запрашиваемый через сторонний API идентификатор модели —`gpt-6.1-sol`. Независимо подтвердить фактическую модель провайдера нельзя. Параметры: reasoning_effort=low, temperature=0.8, top_p=1, max_new_tokens=2048; seed запроса передаётся, но воспроизводимость провайдера не гарантирована. Собственного ограничения входных токенов сейчас нет; доступный контекст и тарификация зависят от провайдера.

## Как проходит адаптивный поиск

Есть три отдельные популяции (islands). Они не являются тремя признаками или тремя окончательными победителями: это три независимые линии поиска со своей памятью. Новые предложения распределяются между ними по кругу. Исправления остаются в той же популяции. Явной миграции или скрещивания программ между популяциями нет.

Два режима различаются памятью:

- **H008, best-only:** каждый запрос содержит лучший по search набор своей популяции и текущую ошибку, если это исправление. Полной истории остальных попыток в сообщениях нет.
- **H009, full own-island history:** в messages API повторно передаётся полный диалог именно этой популяции: прежние запросы, ответы и обратная связь по результатам/ошибкам. Это не постоянная скрытая память провайдера и не история других популяций.

Оба режима используют Python и только сгенерированные признаки. H009 не означает автоматическое добавление исходных15 полей.

Для каждой новой программы:

1. Проверяется синтаксис/AST, разрешённые операции и ограничения.
2. Выявляются уже оценённые структурные дубликаты.
3. На небольших временных снимках проверяются форма, типы, схема, пустая история, отсутствующие группы, перестановка строк и независимость от размера батча.
4. Строится матрица признаков для ВСЕХ сохранённых обучающих пар фолда. С нуля обучается новый LightGBM.
5. На тех же256 search-пользователях скорится весь каталог10000 товаров и считается MAP@12. Этот результат возвращается в поиск.

Параметры дерева фиксированы: binary objective,150 раундов,31 лист, learning_rate=0.05, min_data_in_leaf=100, max_bin=127, feature_fraction=0.9, bagging_fraction=0.8, bagging_freq=1,4 CPU-потока и фиксированные seeds. Это pointwise binary classification с оценкой ранжирования по MAP, не LambdaRank.

Важное отличие от manual/raw baseline: те могут явно помечать свои категории как категориальные, тогда как для сгенерированных f_* такой автоматической пометки сейчас нет.

Построение признаков ограничено60 секундами на вызов; один вызов может содержать80000 пар —8 пользователей×10000 товаров. Worker ограничен8ГБ адресного пространства. Проверки предотвращают многие ошибки, но не доказывают полезность или отсутствие всех смысловых ошибок в признаках.

У невалидного/повторного предложения есть до3 дополнительных попыток исправления. При неизменном исправлении цепочка может завершиться раньше. Ошибки API — отдельные транспортные сбои, а не оценённые feature-наборы. Ответы, программы, ошибки, модели и оценки сохраняются для продолжения без повторной генерации уже полученного ответа.

## Бюджет и отбор

Сначала получали20 успешно оценённых структурно различных программ на режим/фолд. Сейчас продолжаем те же шесть поисковых потоков до30, затем40, сохраняя отбор на каждом пороге. Это не независимые перезапуски20/30/40. Общий лимит —300 фактических POST на режим/фолд, включая унаследованные запросы, исправления и сетевые неудачи.

Структурная уникальность определяется консервативным AST-хешем, а не уникальностью вычисленных чисел. Она не является строгим доказательством смысловой различимости: разные программы могут дать одинаковую матрицу. После первых20 программ число численно различных обучающих матриц было:

- H008:17,15,19 по фолдам;
- H009:20,17,18.

Численная дубликация диагностировалась отдельно и задним числом бюджет/выбор не меняла.

Из каждого поиска берутся три программы с лучшим search MAP и контроль с одним константным признаком. Победителя выбирают по другой, непересекающейся confirmation-группе той же validation-недели. Search и confirmation — разные пользователи. Confirmation-результаты не входят в обратную связь для генерации новых программ. Отдельный heldout validation также не участвует в выборе.

Validation разделяется по пользователям в пропорции60/20/20, но search дополнительно ограничен256 пользователями. Поэтому поиск не использует всю60%-группу. Размеры confirmation приведены в таблице выше. Финальный обученный победитель не переобучается с добавлением validation/test целей.

## Оценка и известные результаты

Outer-test скорится после фиксации отбора, по всем10000 товарам. В текущем продолжении все отборы30/40 должны закончиться и зафиксироваться до outer-оценки этих бюджетов.

В тестовых целях сохраняются все исходные покупки пользователей, включая товары вне ограниченного каталога. Такие покупки невозможно рекомендовать, но они остаются в знаменателе AP; пользователи, купившие только недоступные товары, получают0. Например, на первом фолде таких пользователей563 из1839. Catalog-conditional MAP — отдельная диагностическая метрика, а не замена основной.

Проверенные результаты исходного бюджета20: pooled MAP@12 по5519 user-times трёх фолдов:

| Метод | MAP@12, % |
|---|---:|
|ContextGNN после исправления загрузчика времени|1.2791|
|ID-GNN после исправления загрузчика времени|1.1613|
|Recformer zero-shot|0.6286|
|API GPT H008,20 программ|0.4627|
|API GPT H009,20 программ|0.4514|
|LightGBM manual|0.3473|
|TDM fixed beam64|0.2135|
|LightGBM raw15|0.1415|

Десятичная запись0.4627% означает0.004627 в долях, а не46%. MAP — не доля пользователей с удачной рекомендацией и не доля купленных товаров, угаданных системой.

H008 выше manual на каждой из трёх недель, но95%-интервал их парной разницы включает0. H009 не показал подтверждённого выигрыша над H008; на исходном бюджете20 использовал примерно в4.31 раза больше входных токенов. Итоговые результаты бюджетов30/40 ещё не опубликованы: не следует делать вывод об эффекте увеличения бюджета по отдельным search-значениям.

Изначально в GNN была отдельная ошибка ms/ns при обработке дат, приводившая к пустой истории на validation/test. Она исправлена, обе GNN переобучены; в таблице уже исправленные значения. Аудит временных фильтров API/manual/raw/Recformer/TDM эту ошибку у них не обнаружил. Для ContextGNN одного фолда отдельно задокументированы малые численные различия replay; это не изменение API-протокола.

Метрики пересчитываются независимо по предсказаниям. Неопределённость оценивается парным bootstrap:5000 раз пересэмплируются исходные покупатели с сохранением всех их наблюдений в разных фолдах; считаются интервалы разностей методов. Это не оценка разброса новых seeds/новых временных режимов. Имеются только3 недели и1 seed. Тестовые периоды уже просматривались в прошлых итерациях проекта: это внутреннее сравнение, не окончательный независимый benchmark.

## Что хочу обсудить

Помоги ранжировать улучшения по ожидаемому эффекту, стоимости и тому, насколько чисто их можно проверить. Особенно интересуют:

- Что сейчас сильнее ограничивает метод: данные, видимые LLM, лимит2048 выходных токенов/reasoning=low, память, способ поиска, downstream LightGBM или малая search-выборка?
- Как дать LLM полезную диагностику/статистику без передачи будущих целей и без превращения validation в бесконечно переиспользуемый тренировочный сигнал?
- Имеет ли смысл искать отдельные признаки и их комбинации вместо целых программ; как отделить полезность нового признака от случайного шума?
- Как улучшить память и разнообразие, не оплачивая постоянно полный повтор длинных промптов? Достаточны ли три независимые популяции и один лучший пример?
- Как сравнить AST-дедупликацию с численной/смысловой и корректно учитывать бюджет вычислений?
- Стоит ли отдельно проверить generated-only против manual+generated/raw+generated, категориальные типы и ranking objective?
- Каким контрольным поиском без LLM проверить, что выигрыш даёт именно её выбор признаков, а не сам бюджет перебора?
- Как отличить реальное улучшение от переобучения поиска на256 пользователей? Какая дополнительная временная проверка нужна после выбора идеи?

Предложи3–5 следующих экспериментов. Для каждого задай проверяемую гипотезу, что меняется и что остаётся фиксированным, справедливый бюджет, метрики и критерий успеха. Не объявляй улучшение доказанным только потому, что вырос лучший search MAP.
