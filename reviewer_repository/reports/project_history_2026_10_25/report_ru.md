## 2. Полный RelBench: воспроизведение и ручные baseline

RelBench — набор задач для машинного обучения на связанных таблицах. Основная идея исследуемого подхода — представить строки таблиц как узлы графа, связи по ключам — как рёбра и обучить GNN извлекать признаки из этих связей вместо их ручного составления.

Изначально я просто хотел воспроизвести результат исследователей работы RelBench, чтобы убедиться, что всё сделано правильно и результаты примерно такие же, как в статье.

### 3.2. Двухбашенная GraphSAGE с общими весами

В двухбашенной архитектуре одна ветвь кодирует покупателя, другая — товар. Их векторы сравниваются скалярным произведением: чем выше результат, тем выше товар в рекомендациях. В этом варианте обе ветви используют общие веса GraphSAGE, но обрабатывают покупателя и товар отдельно.

Исследовательская основа этого варианта — [RelBench, раздел 3](https://arxiv.org/html/2407.20060v1#S3): двухбашенная GNN оценивает пары скалярным произведением представлений и обучается с BPR loss. Наш запуск адаптирован из [официального примера gnn_recommendation.py](https://github.com/stanford-star/relbench/blob/919fb8a61a4b4cb787283860597f45701895578d/examples/gnn_recommendation.py). Сам графовый encoder GraphSAGE предложен в работе Hamilton, Ying и Leskovec [«Inductive Representation Learning on Large Graphs»](https://arxiv.org/abs/1706.02216): представление узла строится агрегацией признаков выбранных соседей. Эта исходная статья описывает GraphSAGE в целом; конкретная рекомендательная двухбашенная конфигурация здесь взята из RelBench.

Отдельные forward для пользователя и товара с общим GraphSAGE, dot product 128-мерных векторов, BPR loss и shallow item embedding. Полные 20 эпох, batch 256, ровно 2 000 шагов на эпоху, `uniform` sampling.

Validation/test: **0,57431% / 0,54301%**. Модель ранжировала все 105 542 товара; у прежних ID-GNN/manual использовался локальный pool. Поэтому цифры не являются чистой абляцией головы при одинаковых кандидатах.


## 4. LLM-FE: первые эксперименты с локальной LLM на полном наборе

Идея LLM-FE — поручить языковой модели придумывать признаки и писать код их вычисления. Каждый корректный набор проверяется обучением LightGBM и оценкой на валидации; результат помогает LLM предложить следующий вариант. Так ручной подбор признаков заменяется итеративным поиском с обратной связью. В нашем проекте эта идея адаптирована к связанным таблицам и истории покупок H&M.

Qwen2.5-Coder-7B Q4_K_M работала через отдельный Ollama. LLM формировала SQL-агрегаты истории и производные формулы, LightGBM обучалась на прежних 803 377 парах. Саму LLM не дообучали.

Из 20 предложений измерены только пять, остальные 15 отклонены до MAP. Первые причины: `OVER` — 6, история вне namespace derived — 2, группировки — 2, структура программы — 2, подзапрос — 1, строковый результат — 1, ошибка валидатора `WITHIN GROUP` — 1. Исправление последней само по себе не делало весь ответ корректным.

Выбран лучший кандидат. Вместо полной каталожной оценки была выполнена выполнена отдельная полная оценка на общих кандидатах ID-GNN:

| Метод на общих кандидатах | Validation, % | Test, % |
|---|---:|---:|
| ID-GNN | 2,63442 | 2,78432 |
| Manual LightGBM | 2,09318 | 2,26608 |
| LLM-FE v2 | 0,85428 | 0,81175 |
| LLM-FE H002 | 1,78605 | 1,97540 |

**H002:** ввели бюджет именно успешно оценённых различных наборов, repair loop, уточнили prompt/валидатор и уменьшили поисковый pool до кандидатов ID-GNN. Получены 20 наборов за 83 запроса, 45 repair calls; выбран candidate060. Поиск — 256 validation-пользователей, confirmation — другие 1 024. Полные val/test и точный независимый replay прошли.

Относительно v2 test вырос на **1,16365 п.п.**, но остался ниже manual на 0,29068 п.п. Эффект нельзя приписать только repair loop: одновременно изменились бюджет, интерфейс и кандидаты поиска.

### 7.1. Базовое сравнение на small

| Метод | Validation, % | Test, % |
|---|---:|---:|
| Popularity | 0,26256 | 0,72645 |
| ID-GNN | 4,41072 | 2,65341 |
| ContextGNN | 4,76193 | 3,01558 |
| Two-tower GraphSAGE | 1,55256 | 0,68368 |
| LightGBM manual | 0,99832 | 1,23388 |
| LightGBM ID-GNN features | 0,68531 | 0,96667 |

ContextGNN численно выше ID-GNN, но парный CI разницы включает ноль. Независимые инференсы и пересчёт MAP прошли. Проверялись целостность подвыборки, FK/time и CE value/gradient.

FK/time — проверки связей между таблицами и времени:
- FK (foreign key, внешний ключ): покупки ссылаются на существующих покупателей и товары, ID после создания подвыборки согласованы.
- time: соблюдены временные границы. Например, неделя покупок, используемая как обучающая цель, заканчивается не позже начала validation.

CE value/gradient — проверка функции ошибки:
- CE (cross-entropy, перекрёстная энтропия) — функция ошибки, по которой обучалась модель.
- value — проверяли, что наша реализация возвращает такое же значение ошибки, как простая эталонная формула.
- gradient — проверяли совпадение производных: модель получает такой же сигнал для обновления весов.

### 7.2. Recformer: initial fine-tuning, LR, freeze, дополнительные эпохи

Идея Recformer — представить каждый товар как текст из названий и значений его характеристик, а историю покупателя — как последовательность таких описаний. Transformer кодирует эту историю и формирует представление интересов покупателя, по которому ранжируются товары. [Статья](https://arxiv.org/abs/2305.13731) · [Авторский репозиторий](https://github.com/JiachengLi1995/Recformer) · [Реплика](https://github.com/AaronHeee/RecFormer).

Использована репликация RecFormer, commit `26b00a58…`, внешние предобученные веса и адаптация к недельным многопозитивным целям. Источник весов не аттестован как авторский checkpoint. Это адаптация, не воспроизведение статьи.

| Вариант на small | Validation, % | Test, % | Результат |
|---|---:|---:|---|
| Zero-shot | 2,66996 | 3,30054 | Выше исходного fine-tuning |
| Исходное дообучение, 2+2 эпохи | 2,47022 | 1,23556 | Сильное ухудшение |
| LR 1e−5 + warmup100 + linear decay | 3,55434 | 3,85751 | Улучшение относительно исходного fine-tuning |
| Freeze embeddings + нижние 6 слоёв, constant LR 5e−5 | 1,98481 | 1,76156 | По validation правило с epoch0 выбирает zero-shot |
| Короткий matched-контроль с LR floor | 3,57807 | 3,43889 | Те же веса, что у длинного |
| Длинный опыт с LR floor, остановка на 5 эпохах | 3,57807 | 3,43889 | Дополнительные эпохи не помогли |

Уменьшение LR **вместе** с расписанием дало +2,62196 п.п. test к исходному дообучению, 95% CI [+0,59927; +4,81070]. Вклады LR и расписания отдельно не разделены. Преимущество 3,85751% над zero-shot или ContextGNN не подтверждено интервалами. Первоначальная причина деградации не установлена единственным причинным опытом.

Концентрация рекомендаций уменьшилась: исходный fine рекомендовал 600 различных товаров, LR/warmup — 1 757; самый частый товар встречался у 54,8% и 5,6% test-пользователей. Это наблюдение, не доказательство единственного механизма улучшения.

Длинный запуск планировал до восьми эпох, но остановился после пяти по patience3; короткий и длинный выборы взяли один checkpoint после второй эпохи. Поэтому увеличение реально проверенного горизонта **не улучшило выбранную модель**. Прежний low-LR run с другим decay не является matched-контролем числа эпох.


### 7.3. TDM: фиксированное дерево и кластеризация

TDM организует товары в дерево: листья — отдельные товары, внутренние узлы — их группы. Нейросеть оценивает интерес покупателя к узлам, а поиск идёт от крупных групп к конкретным товарам, отбрасывая менее перспективные ветви. Это позволяет искать рекомендации без оценки каждого товара каталога. [Статья](https://arxiv.org/abs/1801.02294) · [Репозиторий Alibaba](https://github.com/alibaba/x-deeplearning) · [Реализация TDM](https://github.com/alibaba/x-deeplearning/tree/master/xdl-algorithm-solution/TDM).

В эксперименте сравнивались:

- **Fixed** — обучение с заранее заданным деревом товаров.
- **Cluster** — перестроение дерева по сходству обученных векторов товаров, затем обучение новой модели с нуля.
- **Beam64** — поиск сверху вниз с сохранением до 64 перспективных узлов на каждом уровне.
- **Все листья** — оценка всех товаров теми же весами модели, чтобы проверить влияние отсечения ветвей при поиске.

Локальная PyTorch-адаптация, не неизменённый TorchEasyRec и не JTM. Fixed и cluster выбирались по beam64 validation до test. Cluster строился по train-обученным leaf embeddings fixed-модели, затем обучался с нуля.

| Вариант | Validation, % | Test, % |
|---|---:|---:|
| Fixed, beam64 | 1,01601 | 1,39519 |
| Fixed, все листья | 0,93415 | 1,00292 |
| Cluster, beam64 | 0,74588 | 0,55126 |
| Cluster, все листья | 0,67246 | 0,46639 |

## 9. Другая выборка medium: временное сравнение

Medium-v1 была подготовлена и отложена. **До обучения v2** протокол изменён: все исходные validation/test-цели и строки сохранены, недоступные товары не выбрасываются. V1 не является завершённым сравнительным экспериментом.

V2: другие 20 000 покупателей, каталог 10 000; три временных фолда; 5 519 test user-times. Модели и диалоги сбрасывались между фолдами. Earlier outer-недели могли войти в более позднюю историю: это заранее описанная rolling-origin оценка. В каждом API arm/fold — 20 принятых AST-программ; все шесть отборов фиксировались до outer-оценки.

Первоначально завершены 27 оценок девяти методов и replay. Позднее обнаружилось, что **исходные medium ID-GNN/ContextGNN-метрики невалидны**. Их результаты были невероятно малы, поэтому я заподозрил неладное и решил перепроверить их инференс.

### Главная ошибка проекта: миллисекунды прочитаны как наносекунды

Validation/test имели `datetime64[ms]`, а код делил integer timestamp на 10^9, как для ns. Cutoff становился около **1 597 секунд вместо 1,597×10^9**, графовые модели фактически лишались истории покупок. Простая проверка «нет будущих узлов» этого не обнаруживала: пустой временной контекст тоже проходил её.

Диагностика тех же весов fold0 после исправления только cutoff:

- ContextGNN: test **0,0309% → 1,4616%**.
- ID-GNN: test **0% → 1,0529%**.

Это прямое свидетельство влияния ошибки входов, но не итог refit: прежний выбор checkpoint тоже был испорчен. Поэтому отдельно обучены шесть новых GNN и выполнена новая оценка. Manual/raw/API SQL и история TDM/Recformer проверены отдельно: этой ms/ns-ошибкой они не затронуты.

## 10. Medium: изменения ContextGNN и новые товары

ContextGNN сочетает два способа оценки товаров: для товаров внутри выбранного подграфа покупателя GNN вычисляет представления с учётом конкретной пары, а для остальных использует глобальную двухбашенную оценку по векторам покупателя и товара. Оценки согласуются в общем ранжировании. Товар вне подграфа не обязательно новый для покупателя: он мог просто не попасть в выбранную часть истории. [Статья](https://arxiv.org/abs/2411.19513) · [Репозиторий](https://github.com/kumo-ai/ContextGNN).

### Первые три проверки и их сочетание

На прежних search-validation, всего 768 наблюдений, проверены: fanout64/32 вместо32/16, восемь item-кодов как categorical вместо numerical, обучаемая смесь local/global. Проведены девять новых fit и вмешательства в готовые веса.

### 12.2. FEATURE и семантический граф товаров

Режимы FEATURE/FUSION взяты из [реализации ContextGNN](https://github.com/kumo-ai/ContextGNN): представление товара по признакам сравнивается с сочетанием признаков и ID-представления. Источники идеи графового обмена информацией между товарами — **FREEDOM** ([статья](https://arxiv.org/abs/2211.06924), [код](https://github.com/enoche/FREEDOM)) и **PinSage** ([статья](https://arxiv.org/abs/1806.01973)). FREEDOM использует фиксированный граф похожести по содержанию товаров; PinSage объединяет графовые связи и признаки. Наш TF-IDF/one-hot граф и способ его включения в ContextGNN — собственная упрощённая адаптация этих идей.

FEATURE удаляет lookup ID-компоненту RHS, локальный GNN остаётся. Семантический граф — фиксированные TF-IDF описаний + one-hot атрибутов, cosine top20, смесь .5 собственного FUSION-вектора + .5 соседнего. Изображений локально не найдено. Это адаптация идеи, не воспроизведение FREEDOM/PinSage.

| Validation | Matched FUSION | FEATURE | FUSION + semantic graph |
|---|---:|---:|---:|
| Hybrid MAP, % | 1,4754 | 1,4084 | 1,4394 |
| Global MAP, % | 0,5316 | 0,3618 | 0,3692 |
| Hybrid recall доступных новых, % | 2,0810 | 1,4199 | 1,2762 |
| New-only recall доступных новых, % | 2,3346 | 1,6481 | 2,0726 |

На validation улучшение не получено. Для semantic graph global MAP и hybrid new recall имеют отрицательные CI разностей с matched FUSION. Остальные небольшие различия не подтверждены интервалами.

Позже отдельно выполнен test-инференс **FEATURE** из ранее выбранных checkpoint: pooled MAP **1,3111%**, CI [1,0913; 1,5411]%, фолды 1,3933 / 1,1091 / 1,4577%. Это численно выше исторического corrected 1,2791%, но такое сравнение меняет также fanout/типы признаков и не доказывает изолированную пользу FEATURE. Matched FUSION test 1,1595% появился в последующей общей сводке; сам порядок средних также не заменяет парный анализ и независимое подтверждение.

Аудит новых товаров для FEATURE вместе с остальными методами приведён в разделе 13. Подтверждённого test-результата semantic graph в изученной истории нет.

### 12.3. Один и четыре интереса

Источник идеи — **ComiRec**, который представляет интересы пользователя несколькими векторами: [статья «Controllable Multi-Interest Framework for Recommendation»](https://arxiv.org/abs/2005.09347), [репозиторий](https://github.com/THUDM/ComiRec), [реализация моделей, включая ComiRec-SA](https://github.com/THUDM/ComiRec/blob/master/src/model.py). В проекте проверена адаптация attention-pooling этой модели к глобальной ветке ContextGNN, а не полное воспроизведение ComiRec.

Адаптация ComiRec-SA: attention по прошлым товарам sampled-графа, K векторов интереса, максимум dot product по интересам. От оригинального ComiRec отличаются последовательность, позиционные признаки, readout и отсутствие reranker разнообразия. Шесть новых fit K1/K4, три matched FUSION-контроля.

| Вариант | Validation hybrid MAP, % | Test MAP, % | Test recall доступных новых normal / new-only, % |
|---|---:|---:|---|
| Matched FUSION | 1,4754 | 1,1595 | 2,0417 / 2,4806 |
| Attention K=1 | 1,3197 | 0,9677 | 1,2466 / 1,7343 |
| Attention K=4 | 1,4528 | 0,9952 | 1,9878 / 2,3266 |

K4 лучше K1 по test new recall: +0,7412 п.п. normal, CI [+0,3801; +1,1236]; +0,5923 new-only, CI [+0,2037; +0,9958]. Но K4−matched FUSION по MAP **−0,1644 п.п.**, CI [−0,2974; −0,0348]; различия new recall с FUSION включают ноль. Global-only MAP практически одинаков: 0,2890% против0,2904%.

Четыре головы слабо специализировались: cosine запросов 0,99915–0,99981, attention 0,98846–0,99858; одна голова выигрывала 66–86% каталожных сравнений в зависимости от фолда. Четыре вектора не означают четыре независимых вкуса. Текущий вариант **не принят как улучшение FUSION**.

## Вывод

В наших экспериментах исходные графовые модели лучше справлялись с повторными покупками, а LightGBM с признаками, созданными API LLM, показывала более высокий recall новых для покупателя товаров. Графовые модели выигрывали по MAP за счёт повторных товаров, у них аж около 98,6% и 99,5% MAP приходилось на повторные товары, а у H009/40 — лишь 3,6%, то есть его качество преимущественно обеспечивали новые для покупателя товары. То есть несбалансированность полнейшая. Recformer показал промежуточный профиль: сохранял качество на повторных покупках и получал заметную часть MAP за счёт новых для покупателя товаров. 

Интуиция мне подсказывала, что LLM должны дать больший профит, но результаты об этом не говорят.

Возможно, перспективно отдельно решать рекомендации повторных покупок и поиск новых товаров, дабы сбалансировать эффект проверенных методов.
