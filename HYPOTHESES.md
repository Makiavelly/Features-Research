# Гипотезы и возможные эксперименты

Здесь фиксируются идеи до запуска. Результаты завершённых экспериментов

## H001 — Двухбашенная GNN с независимыми весами

Дата добавления: 2026-10-14. Статус: **предложен, не запущен**.
Записано по просьбе пользователя.

**Гипотеза.** Независимые пользовательский и товарный энкодеры могут
лучше специализироваться под разные роли и повысить MAP@12 по сравнению
с двумя ветвями, использующими общий экземпляр GraphSAGE.
Возможен и обратный эффект: рост числа параметров и переобучение.

**Изменение.** Создать два отдельных экземпляра модели с независимыми
параметрами энкодеров признаков, временных энкодеров, GraphSAGE и выходных
проекций. Ветвь пользователя вычисляет u(user, time), ветвь товара —
v(item, time). Векторы имеют размер 128; скор пары u·v; обе ветви совместно
обучаются BPR loss. Товарный shallow embedding сохраняется в товарной
ветви. Graph data и sampler могут быть общими: это не разделяемые веса.

**Контроль.** Текущий shared-backbone запуск
`hm_twotower_sage_seed_42_v1`, задача `rel-hm/user-item-purchase`.
Для будущего варианта зарезервирован отдельный идентификатор
`hm_twotower_independent_seed_42_v1`; его артефакты должны храниться отдельно.
У существующей heterogeneous GNN уже есть параметры по типам узлов и
связей; эксперимент проверяет именно независимость двух полных сетей.

**Протокол сравнения.** Те же данные и временные границы, seed 42,
train batch 256, 20 эпох, 2000 шагов/эпоху, Adam lr=.001, 2 слоя,
128 каналов, sum aggregation, uniform temporal sampling, тот же способ
выбора позитивов/негативов и фиксации RNG при оценке. Оценка на полном
каталоге 105,542 товаров. Выбирать checkpoint по validation; test
использовать для финальной оценки, без подбора параметров по test.

**Что сохранить.** Полный validation/test MAP@12, кривые loss и validation,
число обучаемых параметров, время обучения/инференса, пиковую память GPU,
конфигурацию, best/last checkpoints, пользовательские и товарные векторы.
Проверить инференс в отдельном процессе после загрузки сохранённых весов.
Сопоставить разницу MAP с контрольным запуском в процентных пунктах.

**Ограничения.** При независимых сетях увеличится число параметров:
результат отражает одновременно разделение весов и увеличение ёмкости.
Вариант с сопоставимым числом параметров потребует отдельного протокола.
Один seed даёт предварительный вывод; устойчивость преимущества без
повторных запусков не установлена. Если понадобится уменьшить batch
из-за памяти, изменение явно зафиксировать и подобрать сопоставимый контроль.

**Связь со статьёй.** В проверенной статье RelBench и приложении B.3
сравнение общих весов с независимыми весами двух башен не найдено;
опубликованных метрик этого варианта нет. Это наша исследовательская гипотеза.
[RelBench](https://arxiv.org/html/2407.20060v1).

## H002 — Больше проверенных LLM-наборов: отдельный бюджет и исправление программ

Дата добавления: 2026-10-15. Статус: **выполняется: hm_llmfe_qwen25coder7b_seed42_h002_shared_v1**.
Записано по просьбе пользователя: получить как можно больше реально
проверенных наборов признаков, не исчерпывая поиск ошибочными генерациями.

**Основание.** В LLM-FE v2 из 20 предложений только пять прошли вычисление
признаков, обучение LightGBM и оценку search MAP@12. Остальные отклонены
из-за ошибок/ограничений интерфейса, поэтому их полезность не измерена.

**Гипотеза.** Раздельный учёт запросов к LLM и успешно оценённых наборов,
вместе с циклом исправления программ, позволит проверить больше различных
наборов и найти признаки с более высоким validation/test MAP@12.

**Изменение протокола.**
- Задавать целевое число успешно оценённых различных наборов отдельно от
  предельного числа обращений к LLM. Ориентир из обсуждения — 20 оценённых
  наборов при бюджете до 100 обращений; окончательные числа закрепить
  перед запуском. Цель — увеличить число проверенных наборов, эти числа
  не являются уже запущенным экспериментом или универсальным максимумом.
- Для ошибочной программы передавать LLM конкретную причину и саму программу,
  запрашивать исправление, повторно проверять и только затем обучать модель.
  Ограничение числа исправлений одного предложения определить в конфигурации.
- В общий бюджет обращений включать как новые предложения, так и исправления.
  Ошибка не увеличивает счётчик успешно оценённых наборов.
- Считать набор проверенным только после полного вычисления его признаков,
  обучения LightGBM и получения search validation MAP@12 по всему каталогу.
  Smoke-проверки и точные дубликаты программ не считать новыми проверенными
  наборами. Сохранять хеши программ и историю исправлений.
- До запуска устранить известные ложные отказы валидатора и яснее задать
  доступные столбцы/операции. Не добавлять формулы признаков вручную;
  исправления должна предлагать локальная LLM.

**Контроль и оценка.** Сопоставлять с `hm_llmfe_qwen25coder7b_seed42_v2`:
та же модель LLM, seed 42, исходные данные, обучающие пары и параметры
LightGBM; те же временные границы и весь каталог. Поиск/выбор только по
validation, отдельная confirmation-проверка, test для итоговой оценки.
Новый протокол получает новый run_id и отдельные артефакты. Текущий v2
не менять и не перезапускать в рамках этой записи.

**Что измерять.** Число обращений, исправлений и различных оценённых наборов;
долю успешных программ и причины отказов; затраты времени/токенов;
лучший MAP по числу запросов и по числу проверенных наборов; полные итоговые
validation/test MAP@12. Сохранить кривые обучения LightGBM по boosting rounds
и графики прогресса поиска.

**Ограничения.** Больше попыток повышает риск подгонки под search validation;
нужны отдельная проверка выбора и неизменный test. Преимущество может
отражать увеличенные вычислительные затраты вместе с улучшением исполнения;
эти эффекты следует явно разделять при интерпретации. Результатов H002 пока нет.

### H002 — закреплённый протокол запуска 2026-10-15

Run ID: `hm_llmfe_qwen25coder7b_seed42_h002_shared_v1`.
Пользователь поручил проверить H002, разрешил больше2 потоков LightGBM,
затем прямо отменил полный каталог при поиске и потребовал меньшую выборку.
Эти указания заменяют первоначальное условие полного каталога для H002.

- Цель20 различных полностью обученных/оценённых наборов, до100 запросов
  LLM суммарно, включая до2 исправлений каждого предложения.
- Поиск: прежние фиксированные256 validation пользователей, но теперь
  только их сохранённые кандидаты ID-GNN (~28 товаров/пользователь).
- До3 лучших наборов: другие1024 validation пользователя, тот же тип пула.
- Итог: все validation/test пользователи на точных общих кандидатах ID-GNN;
  независимый полный повтор из сохранённой модели на2 потоках.
- Qwen2.5-Coder7B Q4_K_M, seed42; прежние803377 train пар/50000 user-times;
  LightGBM150 rounds/leaves31, прежние seeds42, обучение/инференс8 потоков.
- Дубликаты: хеш формул без rationale, названий признаков, регистра SQL,
  пробелов и порядка группировочных ключей; не алгебраический анализ эквивалентности.
- Известный ложный отказ WITHIN GROUP устранён только в режиме H002.
  Smoke/preflight и дубликаты не засчитываются в20 оценённых наборов.
- Сохраняются все запросы/ответы/ошибки, исправления, токены/время,
  train logloss по150 rounds, кривые поиска и итоговые AP-гистограммы.
- Новый протокол одновременно меняет бюджет, исправления, prompt, валидатор
  и пул поиска: изолировать вклад одного изменения нельзя. Старые search MAP
  по всему каталогу с новыми search MAP напрямую не сравнивать.
- V2 и его пауза остаются без изменений; старые результаты не перезаписываются.
- При подготовке test_h002 выявил, что quantile_cont WITHIN GROUP не поддержан
  установленным DuckDB. Тест исправлен на поддерживаемый mode() WITHIN GROUP;
  формулы LLM автоматически не переписываются. Все6 поведенческих тестов прошли.
