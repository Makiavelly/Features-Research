# Локальная LLM → признаки → LightGBM

Запуск `hm_llmfe_qwen25coder7b_seed42_v1` — адаптация LLM-FE к
`rel-hm/user-item-purchase`. Это новый эксперимент, не воспроизведение
опубликованных ranking-метрик. Основная метрика — MAP@12 по всему каталогу.

## Модель и окружение

- Qwen2.5-Coder-7B-Instruct, GGUF Q4_K_M, отдельный Ollama на localhost:11435.
- Веса внутри `data/models/ollama_llmfe`; прежний Ollama и его модели не меняются.
- Метаданные, digest весов, версия сервера и фактическое размещение в памяти
  сохраняются в `results/qwen25coder7b_seed42_v1/model_manifest.json` и `llm_runtime.json`.
- Контекст 4096, температура .8, максимум 1800 выходных токенов; последовательные
  генерации. Seed модели и LightGBM 42, seed отдельных предложений 42+i.
- Используется существующий `RelBenchGNN/.venv-wsl`, без изменения пакетов,
  драйвера и окружения unsloth. Ollama использует собственный llama.cpp runner.

## Какие признаки создаёт LLM

Каждая программа — JSON с SQL-выражениями агрегатов и производных признаков.
LLM выбирает группировки, временные окна, формулы и взаимодействия.
Разрешены группы пользователь, товар, пара пользователь–товар,
пользователь–категория. Host компилирует выражения в DuckDB и выполняет joins.
Это ограниченное пространство программ; результат не характеризует все
возможные Python/SQL-программы или все LLM.

Исходные входы — age/FN/Active/статусы клиента и числовые поля товара
(список в features.py); строки статусов кодируются категориями.
Свободные тексты и postal_code не используются. История включает прошлые
транзакции с категориальными полями товара и возрастом покупателя.
Старые ручные агрегаты, GNN-векторы и GNN scores не входят в признаки/промпты.
В prompt включаются пять train-примеров, описание схемы и предыдущая удачная
программа своего острова. Конкретные исторические признаки не задаются вручную.

Из прежнего manual_v1 читаются **только** customer_id/article_id/timestamp/label,
чтобы сохранить те же 50,000 user-time строк и 803,377 обучающих пар.
Выбор строк/отрицательных пар исторически использовал seed 2026; это сохранено.
ID/label/time не становятся признаками. Модель GNN обучалась на большем объёме.

## Поиск и оценка

1. Контроль сырых статических признаков: те же LightGBM и search users.
2. 20 предложений LLM, 3 острова памяти, одно удачное решение в prompt.
   Ошибочные предложения сохраняются и входят в бюджет; текст ошибки передаётся
   следующему предложению этого острова. Остров хранит валидные решения,
   в prompt попадает лучшее. Это адаптация, без полноценной paper island-migration.
3. Каждое валидное предложение: 150 rounds LightGBM binary, 31 leaves,
   lr=.05, min_leaf=100, фиксированные параметры; подбор по полному каталогу
   для 256 validation пользователей (seed42).
4. До 3 лучших различных программ подтверждаются на других 1024 validation
   пользователях. Выбор программы фиксируется **до** чтения test-метрик.
5. Лучшая LLM-программа оценивается на всех 74,575 validation и 67,144 test
   пользователях, каталог 105,542. Полное покрытие, без приблизительного retrieval.
6. Дополнительно — те же сохранённые кандидаты, что у ID-GNN seed42.
7. Отдельный процесс проверяет повторный инференс на 32 фиксированных
   пользователях каждого split по полному каталогу. Это проверка подмножества,
   не повтор всей финальной оценки. Все основные метрики — после reload модели.

Вычисления выполняются пакетами по 8 пользователей. Для любого одинакового
score применяется article_id ascending. Финальные предсказания сохраняются
в .npy, прогресс — после каждого пакета; процесс можно продолжить после остановки.
Конечные validation/test полные, search/confirmation/smoke явно отдельные.

ID-GNN оценивает sampled товары, а остальные scores в полном каталоге равны 0.
Поэтому основной результат сравнивает полные конвейеры; общий pool дополнительно
изолирует ранжирование. Ранее опубликованные/локальные метрики не перезаписываются.

## Изоляция и проверки

LLM пишет только выражения: SQL statements/subqueries, неизвестные функции,
файловый доступ и исполняемый Python запрещены. Labels не регистрируются
в feature engine. История автоматически ограничена `t_dat <= cutoff`.
Тесты проверяют границу cutoff, нечувствительность к будущим транзакциям и
меткам, отсутствие ID в признаках и точный full-catalog top-k с ties.
Evaluator — отдельный процесс с лимитом времени (6h search / 7d final),
DuckDB 2300MB памяти и до 6GB временных файлов.

## Запуск и восстановление

Из PowerShell в корне проекта:

```powershell
.\LLMFeatures\launch.ps1
Get-Content LLMFeatures/results/qwen25coder7b_seed42_v1/pipeline.log -Tail 30
```

Первичная загрузка модели выполняется `bash LLMFeatures/setup_model.sh`.
Перед восстановлением проверить PID и процессы WSL; не создавать дубликаты.
Процесс pipeline ждёт завершения setup, проверяет тесты и автоматически
проходит поиск, оценку, проверку и построение отчёта. Изменения протокола
после начала требуют нового run_id. Сбои/отклонённые программы остаются в истории.

Артефакты: `LLMFeatures/results/qwen25coder7b_seed42_v1`.
Кэш исходных обучающих пар/SQL spill: `baseline/cache/llmfe_qwen25coder7b_v1`.
Итоговый отчёт после финальной проверки: `reports/llmfe_qwen25coder7b_v1`.

Источники: https://arxiv.org/html/2503.14434v3,
https://github.com/nikhilsab/LLMFE,
