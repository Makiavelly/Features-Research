# H009: история сообщений через API

Новый независимый API-поток после H008. Меняется память генерации: при каждом
запросе передаётся список messages с полной историей только текущей популяции.
В диалоге сохраняются предыдущие user-запросы, полный assistant-код, результаты
проверки (включая отказы) и search MAP. Текущее задание также содержит лучший код
своей популяции, как H008. Confirmation/test не используются в диалоге.

Три диалога изолированы по популяциям. Общий бюджет20 валидных программ/300 POST,
до3 исправлений; seed42. Пары72813, каталог5000,LightGBM150/31/4CPU, интерфейс
полного Python и только возвращённые f_* входы дерева полностью совпадают с H008.
Одна константа — служебный контроль. Статические атрибуты доступны функции,
их явное возвращение моделью разрешено; автоматического добавления raw15 нет.

Сообщения восстанавливаются из сохранённых фактических API-запросов, ответов и
trial.json. Resume не теряет историю и не создаёт второй запрос для сохранённого
ответа. HTTP/transport-попытки считаются в общем лимите300.

История не обрезается и не суммируется. Максимальное окно провайдера независимо
не установлено: при отказе из-за контекста запуск остановится с сохранением выходов.
Фактические input/output токены записываются. Это равный бюджет попыток, но не
равный бюджет входных токенов по сравнению с best-only H008.

До API:13 синтетических проверок диалога и mocked-адаптера без сети; повторное
использование33 проверок валидатора обосновано точным совпадением файлов движка,
worker и текущего prompting с H008. Отдельный аудит проверит messages каждого
фактического запроса, отсутствие чужих популяций и всю цепочку обратной связи.

Search128 → top3+контроль → confirmation88 → заморозка → heldout88/val304/test250.
Предыдущие запуски не изменяются. Один seed и повторно используемый test не
позволяют доказать универсальное преимущество памяти.

Runner: run_provider_history.py. Реестр: reports/provider_history_v1/current_run.json.
