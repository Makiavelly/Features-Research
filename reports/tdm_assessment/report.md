## Что подтверждено в коде

XDL: `xdl-algorithm-solution/TDM/script/tdm_ub_att_ubuntu/train.py`
использует XDL/MXNet, Python2 (`xrange`, print statements), HDFS,
libselector.so и TDMOP/TDMPREDICTOP. Есть attention-DNN, экспорт embeddings,
построение и кластеризация дерева. Wiki требует старый Docker/MXNet1.3,
сборку C++/SWIG. Реальный TDM есть, но восстановление стека выглядит
невыгодным для нашего пилота. Исполнимость не проверена.

TorchEasyRec: подтверждён более удобный готовый TDM и локальный Parquet pipeline:

| Путь upstream | Содержание |
|---|---|
| tzrec/models/tdm.py | TDM(RankModel), MultiWindowDINEncoder, MLP, экспорт item embeddings |
| tzrec/modules/sequence.py | Attention с query от кандидата; windows_len — число позиций истории, timestamp encoder не использует |
| tzrec/datasets/sampler.py | TDMSampler, положительные предки и негативы по уровням; TDMPredictSampler |
| tzrec/tools/tdm/init_tree.py | Инициализация дерева |
| tzrec/tools/tdm/gen_tree/tree_generator.py | Сортировка категория/ID, рекурсивное деление |
| tzrec/tools/tdm/gen_tree/tree_builder.py | Общая глубина листьев, отдельные ID внутренних узлов, мода категорий/среднее числовых атрибутов |
| tzrec/tools/tdm/cluster_tree.py и gen_tree/tree_cluster.py | KMeans и балансировка по embeddings |
| tzrec/tools/tdm/retrieval.py | Поиск сверху вниз, финальная сортировка/дедупликация, recall_ids |
| docs/source/quick_start/local_tutorial_tdm.md | Дерево → обучение → экспорт → clustering → переобучение → retrieval |
| examples/tdm_taobao.config | Конфигурация модели и признаков |

Retrieval этой ревизии сохраняет 2*recall_num внутренних узлов, а на листьях
recall_num. Начальный уровень зависит от recall_num: настройки примера
нельзя механически переносить на маленькое дерево. Встроенная метрика
проверяет попадание одного target item, не наш недельный MAP@12.

Runtime требует GraphLearn/pyfg и другие пакеты; проверенные GPU/CPU
requirements фиксируют torch2.14, TorchRec/FBGEMM. Это другой стек,
чем проектный torch2.2.2. Документация предлагает cu126/cu130/CPU.
Для cu130 заявлен минимум драйвера580.65.06, на проектной машине528.02.
cu126 имеет другой заявленный минимум: нельзя объявлять весь TorchEasyRec
несовместимым без отдельной проверки. Пример с8процессами не доказывает
необходимость8GPU; однопроцессный запуск/VRAM/время пока не проверены.

## Отличие второй статьи

TDM: дерево товаров + модель интереса к узлам, обучение на положительных
путях и негативных узлах того же уровня; поиск beam search. Первоначальное
дерево можно перестраивать по обученным embeddings через балансируемый KMeans.

JTM: чередование обучения модели и назначения товаров листьям по общей
функции качества предсказания; сегментированное назначение с ограниченной
ёмкостью узлов. История на уровне дерева представляется предками купленных
товаров того же уровня. Простая кластеризация embeddings не является JTM.

В деревьях путей нет JTM/assignment, в проверенных TDM-модулях перестройка
использует KMeans. Готовый JTM в этих двух репозиториях НЕ подтверждён.
Это вывод в пределах проверенного кода, не утверждение об отсутствии JTM
во всём GitHub. Точное max-heap свойство является предпосылкой теории;
обычная обученная сеть не гарантирует его и безошибочный поиск.

## Адаптация и предлагаемый протокол

Это рекомендации перед новым заданием; запуск не поручен.

1. Сохранить small-v1: 4804/304/250 user-time и весь каталог5000.
   Большой H&M с105542товарами — отдельный опыт. На малом каталоге реальное
   ускорение дерева не гарантировано из-за накладных расходов обхода.
2. Готовить историю на timestamp каждой строки по прежнему past-only правилу.
   Не превращать недельные цели в next-event задачу. Повторные покупки
   разрешить, пустую историю и порядок одинаковых дат обработать явно.
3. Передавать все положительные товары недели; исключать их и всех их
   предков из негативов соответствующего уровня. Готовый sampler принимает
   один item ID и явно не знает недельное множество. Зафиксировать веса
   user-time/позитивов/уровней. Старые72813binary-пар не являются готовыми
   TDM-примерами: основа сравнения — исходные4804строки и недельные цели.
4. Все товары должны иметь уникальные листья, включая непривычные5000,
   не степень2. Согласовать статические категории H&M, признаки внутренних
   узлов, item/node mappings и padding: article_id0 у нас валиден.
5. Дерево/embeddings учить только по train; val для выбора, test после
   фиксации решения. Кластеризация по val/test целям недопустима.
   Транзакции, наблюдённые к test cutoff, можно использовать как историю
   по прежнему протоколу, без дообучения на test целях.
6. Различать позиционные окна windows_len и интервалы дней; зафиксировать
   длину истории. Замена на дневные окна — изменение подготовки/encoder.
7. Подключить наш MAP@12 по множеству недельных целей, одинаковый user order,
   полный кандидатный каталог и ties. Полный каталог допустимых кандидатов
   не означает вычисление score каждого товара при beam search.
8. Сохранять checkpoint вместе с деревом, mapping, encoder и конфигурацией;
   независимый процесс повторяет прогнозы. Дополнительно измерять Recall@K,
   coverage, долю целей с обучавшимися листьями, оценённые узлы, VRAM,
   время обучения/поиска/построения дерева. Sampled AUC не заменяет MAP.

Рекомендуемая последовательность отдельных опытов: fixed-tree TDM;
затем TDM с одним перестроением по собственным train-learned embeddings;
затем JTM с дополнительным кодом. Для первого опыта полезно сравнить
beam и полный скоринг листьев теми же весами: это контроль влияния поиска,
не изолированная проверка иерархического обучения. Последняя потребовала бы
отдельного DNN без обучения внутренних узлов.

Из двух upstream предпочтителен TorchEasyRec: отдельное совместимое
окружение или явный перенос нужных частей в проектный PyTorch. Перенос
должен называться нашей адаптацией. Существующие окружения не менять.
Компактный TDM выглядит реалистичным для ресурсов, но VRAM/часовой бюджет
и преимущество над ContextGNN/Recformer не измерены.

Для исследовательской цели это отдельный рекомендатель/генератор кандидатов.
TDM→LightGBM или embeddings/score как признаки — отдельные последующие
эксперименты с учётом candidate recall и утечек при обучении ranker.
